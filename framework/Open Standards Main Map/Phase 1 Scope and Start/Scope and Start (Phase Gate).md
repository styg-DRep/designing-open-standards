# Scope and Start

## Intent

Determine whether a proposed open governance standard is sufficiently understood, justified, scoped, supported, and sustainable to move from exploration into committed development.

Scope and Start is not simply the end of preliminary planning.

It is the point where the standards effort must demonstrate:

> **We understand enough about the opportunity, the ecosystem, the intended change, the proposed intervention, the people involved, and the work ahead to justify beginning development.**

The phase should also preserve the possibility that the correct outcome is:

- reframe;
    
- adopt an existing standard;
    
- extend an existing standard;
    
- use a different intervention;
    
- pause;
    
- or stop.
    

A standards process that cannot legitimately choose not to create a standard is not doing meaningful scoping.

---

# Core question

The Scope and Start gate asks:

> **Is there a sufficiently strong, evidence-informed, participatory, and sustainable case for this standards effort to enter development?**

---

# Scope and Start is an aggregation gate

It does not replace the nodes beneath it.

It draws upon them.

The phase should be considered successful only when the outputs of those nodes form a coherent whole rather than a collection of completed exercises.

The principal inputs are:

- Simple Canvas
    
- Frame the Opportunity
    
- Types of Standards
    
- Understand the Ecosystem
    
- Actor Map
    
- Existing Standards inquiry
    
- Identify Community Stakeholders
    
- Decide Who to Work With
    
- Decide on Aims and Objectives
    
- Minimal Theory of Change
    
- Core Features
    
- Interoperability Intent
    
- Adaptability and Extensibility
    
- Inclusivity
    
- Real-World Test Intent
    
- Development Principles
    
- Choose Development Method
    
- Plan Development
    
- Think About Sustainability
    
- Approval / mandate record
    

---

# The Scope and Start Bundle

The primary output is a **Scope and Start Bundle**.

This is not necessarily one document.

It is the coherent set of artifacts, decisions, evidence, and unresolved questions required to enter development responsibly.

The bundle should contain enough information that a new participant could understand:

1. why the effort exists;
    
2. what condition it seeks to change;
    
3. who is involved or affected;
    
4. what already exists in the ecosystem;
    
5. why a standard may be appropriate;
    
6. what kind of standard is being considered;
    
7. what the effort intends to achieve;
    
8. how the standard is expected to contribute to change;
    
9. what will initially be developed;
    
10. how the work will be developed and tested;
    
11. how decisions and contributions will be governed;
    
12. whether the work can be sustained;
    
13. what remains uncertain.
    

---

# Bundle Component: Opportunity Frame

The bundle should contain a clear description of:

- current condition;
    
- affected actors;
    
- consequences;
    
- coordination need;
    
- desired difference;
    
- competing frames;
    
- evidence;
    
- assumptions;
    
- open questions.
    

The opportunity should remain intelligible independently of the proposed standard.

If the opportunity can only be described as:

> We need a standard for X

then scoping is incomplete.

---

# Bundle Component: Ecosystem Understanding

The effort should have a usable understanding of the environment in which the standard would operate.

This should include:

- actors;
    
- governance activities;
    
- relationships;
    
- information flows;
    
- infrastructure;
    
- existing standards;
    
- institutional dependencies;
    
- relevant control points;
    
- political tensions;
    
- stakeholder groups;
    
- important unknowns.
    

The purpose is not exhaustive mapping.

The question is whether development would otherwise proceed against an imagined ecosystem.

---

# Bundle Component: Actor Map

The Actor Map should make visible:

- who produces relevant governance activity;
    
- who uses relevant governance infrastructure;
    
- who exchanges or transforms governance information;
    
- recurring governance roles;
    
- actor gaps;
    
- infrastructure dependencies;
    
- likely relationship leads.
    

This provides the descriptive base from which stakeholder relevance and participation choices have been made.

---

# Bundle Component: Standards Landscape

The effort should demonstrate that it has searched for existing coordination before creating new coordination.

Record:

- relevant standards;
    
- de facto conventions;
    
- vocabularies;
    
- schemas;
    
- protocols;
    
- guidance;
    
- infrastructure;
    
- existing communities of practice.
    

For each relevant candidate ask:

- Can it be used directly?
    
- Can it be extended?
    
- Can it be opened?
    
- Can it supply building blocks?
    
- Why is a new standard still justified?
    

---

# Pattern: Earn the Right to Create

The Scope and Start bundle should include a short **new-standard rationale**.

Not:

> No suitable standard exists.

But:

> We examined A, B, and C. A solves part of the semantic problem but not the exchange requirement. B could be extended but its governance does not permit the required use. C solves a neighboring problem but introduces incompatible assumptions. Therefore a new standard, reusing X and Y, appears justified.

This makes the decision auditable.

---

# Bundle Component: Standard Classification

Using the Types of Standards reference cluster, record:

```
coordination_need:
standardization_surface:
primary_type:
secondary_types:
likely_products:
required_strength:
```

This should remain simple.

Its function is to orient later development, not force the standard into a rigid taxonomy.

---

# Bundle Component: Stakeholder and Participation Model

The effort should distinguish:

- actors;
    
- affected stakeholders;
    
- contributors;
    
- shapers;
    
- early adopters;
    
- testers;
    
- advocates;
    
- stewards.
    

The bundle should record:

- who has been identified;
    
- who has actually participated;
    
- who has been contacted;
    
- who remains missing;
    
- where representation is weak;
    
- who is expected to participate during development.
    

Do not convert a stakeholder map into a claim of community consent.

---

# Bundle Component: Aim and Objectives

The effort should state:

## Aim

What broad ecosystem change the standard seeks to contribute toward.

## Objectives

What meaningful capabilities or conditions must be created for that aim to become more likely.

The objectives should be:

- meaningful;
    
- traceable;
    
- plausible;
    
- bounded;
    
- testable;
    
- revisable.
    

They should not merely list deliverables.

---

# Bundle Component: Minimal Theory of Change

The bundle should make the causal logic visible.

At minimum:

```
CURRENT PATTERN
      ↓
STANDARD INTERVENTION
      ↓
CHANGE MECHANISM
      ↓
NEAR-TERM OUTCOME
      ↓
CHANGED ECOSYSTEM PATTERN
      ↓
INTENDED IMPACT
```

with explicit:

- enabling conditions;
    
- assumptions;
    
- risks;
    
- unintended effects;
    
- learning questions.
    

The theory of change need not be sophisticated.

It needs to be explicit enough that development is not based on invisible causal assumptions.

---

# Bundle Component: Core Scope

The effort should define what the first meaningful development target includes.

Record:

- core features;
    
- optional features;
    
- explicitly deferred features;
    
- interoperability requirements;
    
- extension boundaries;
    
- accessibility requirements;
    
- translation needs;
    
- testing requirements.
    

---

# Pattern: Scope Is Also Exclusion

A good scope should state not only what is included but what is **not currently being standardized**.

For example:

```
in_scope:
  - proposal metadata vocabulary
  - exchange schema
  - provenance fields

out_of_scope:
  - voting interface design
  - wallet implementation
  - constitutional interpretation
```

Explicit exclusions help prevent standards efforts from becoming general-purpose governance reform projects.

---

# Bundle Component: Use Cases

Use cases should demonstrate how the proposed standard is expected to function in real situations.

Each important use case should identify:

- actor;
    
- context;
    
- interaction;
    
- relevant standard capability;
    
- expected outcome.
    

At least some use cases should come from prospective adopters rather than only from the standards team.

---

# Bundle Component: Development Method

Record how the standard will be developed.

The development method should explain the balance between:

- exploration;
    
- iteration;
    
- consensus;
    
- formal review;
    
- testing;
    
- release.
    

The method should fit the level of uncertainty and the legitimacy requirements of the effort.

---

# Bundle Component: Development Plan

The development plan should include:

- work phases or cycles;
    
- development units;
    
- prioritized features;
    
- contributors;
    
- roles;
    
- testing;
    
- engagement;
    
- decision points;
    
- infrastructure;
    
- release criteria;
    
- decision rights.
    

The plan should be detailed enough to begin work without pretending that all future work is predictable.

---

# Bundle Component: Contribution and Intellectual Property Model

The effort should define how people can contribute and what happens to their contributions.

At minimum:

- contribution process;
    
- contributor attribution;
    
- rights granted by contributors;
    
- ownership or stewardship of collective work;
    
- license for the standard;
    
- licensing of code or supporting artifacts where relevant.
    

For an open standard, rights should support broad access, implementation, reuse, and redistribution.

Do not treat licensing as a launch-stage afterthought.

---

# Bundle Component: Governance and Change Model

Even before the first release, the effort should know how development decisions will be made.

Record:

- who can propose changes;
    
- who evaluates them;
    
- who decides;
    
- how decisions are documented;
    
- how objections are handled;
    
- how scope can change;
    
- how deadlock is addressed;
    
- how authority can be transferred.
    

This may initially be lightweight.

It should nevertheless be explicit.

---

# Bundle Component: Sustainability Model

The standards effort should demonstrate that its likely future burden has been considered.

Include:

- startup resources;
    
- ongoing resources;
    
- maintenance surface;
    
- stewardship model;
    
- technical dependencies;
    
- adopter burden;
    
- contributor continuity;
    
- knowledge preservation;
    
- likely support needs;
    
- sustainability risks.
    

---

# Bundle Component: Development Infrastructure

Record where the work will happen.

Possible elements include:

- repository;
    
- issue tracker;
    
- discussion space;
    
- decision log;
    
- documentation;
    
- test data;
    
- validator;
    
- meeting archive;
    
- communication channels.
    

The infrastructure should support:

- transparency;
    
- persistence;
    
- contribution;
    
- testing;
    
- public visibility.
    

---

# Bundle Component: Engagement Channels

Record how participants can:

- discover the effort;
    
- follow progress;
    
- provide feedback;
    
- contribute;
    
- test;
    
- raise objections;
    
- receive updates.
    

Distinguish:

**broadcast channels**

from

**participation channels**.

A newsletter informs.

An issue tracker, workshop, or deliberative forum may enable contribution.

Both can matter, but they are not interchangeable.

---

# Bundle Component: Testing Intent

The effort should identify how reality will challenge the developing standard.

Record:

- key test scenarios;
    
- early adopters;
    
- expected test environments;
    
- interoperability tests;
    
- semantic tests;
    
- implementation tests;
    
- process tests;
    
- likely failure conditions.
    

Testing should already be embedded in the development plan.

---

# Bundle Component: Risks and Open Questions

The bundle should preserve uncertainty.

Record:

- major known risks;
    
- assumptions;
    
- unresolved disputes;
    
- weak evidence;
    
- missing stakeholders;
    
- unknown technical dependencies;
    
- unresolved governance questions.
    

Do not treat the transition to Development as evidence that these no longer exist.

---

# Pattern: Open Questions Travel With the Work

Every unresolved question should either:

- become a development task;
    
- become a test hypothesis;
    
- become a monitoring condition;
    
- become a review trigger;
    
- or be explicitly accepted as a known uncertainty.
    

Unknowns should not disappear merely because the phase ends.

---

# Scope and Start Gate Criteria

A standards effort is ready to enter Development when the following are sufficiently true.

## Opportunity

- The current condition is clearly described.
    
- The coordination need is plausible.
    
- The intended beneficiaries and affected actors are known.
    
- Competing interpretations have been considered.
    

## Ecosystem

- Relevant actors and infrastructure have been mapped.
    
- Important relationships and dependencies are visible.
    
- Existing standards have been investigated.
    
- Major power and control considerations have been surfaced.
    

## Justification

- There is a defensible reason to standardize.
    
- Existing standards are insufficient or require explicit extension.
    
- The proposed standardization surface is clear.
    
- The scope is bounded.
    

## Participation

- Relevant stakeholders have been identified.
    
- Meaningful participants are available for development.
    
- Early adopters or testers have been identified.
    
- Important representation gaps are acknowledged.
    

## Purpose

- The aim is clear.
    
- Objectives describe meaningful change rather than outputs.
    
- The causal logic is plausible.
    
- Important assumptions are explicit.
    

## Design Intent

- Core capabilities are identified.
    
- Interoperability expectations are visible.
    
- Extensibility boundaries are understood.
    
- Accessibility needs have been considered.
    

## Development

- A development method has been selected.
    
- A practical development plan exists.
    
- Testing is embedded.
    
- Development infrastructure exists or is ready.
    
- Decision rights are explicit.
    

## Openness

- Contribution conditions are clear.
    
- licensing is appropriate;
    
- provenance can be preserved;
    
- development is inspectable.
    

## Sustainability

- Initial resources are credible.
    
- Ongoing burdens are visible.
    
- Stewardship is plausible.
    
- Adoption burden is proportionate.
    
- The standard can survive individual contributors.
    

## Mandate

- The relevant actors have approved, consented to, or otherwise accepted progression.
    
- Approval conditions and objections are preserved.
    

---

# Pattern: Readiness Is Sufficient, Not Complete

Do not require perfect certainty.

The gate asks whether the work has enough coherence to enter a phase where implementation and testing can produce new knowledge.

Some questions can only be answered through development.

The relevant distinction is:

> **Is this an uncertainty we must resolve before development, or an uncertainty development is intended to resolve?**

---

# Possible Gate Outcomes

## 1. Enter Development

The case is sufficiently coherent and supported.

Edge:

**Scope and Start —gates→ Develop**

---

## 2. Enter Development Conditionally

Development may proceed subject to explicit conditions.

Examples:

- secure a second early adopter;
    
- resolve licensing;
    
- test one key interoperability assumption;
    
- recruit missing technical stewardship.
    

Conditions remain attached to the development bundle.

---

## 3. Return to Frame the Opportunity

Use when:

- the opportunity remains vague;
    
- competing frames are unresolved;
    
- ecosystem evidence contradicts the original framing.
    

Edge:

**Scope and Start —returns-to→ Frame the Opportunity**

---

## 4. Return to Understand the Ecosystem

Use when:

- important actors are missing;
    
- critical infrastructure remains unknown;
    
- power relationships are poorly understood;
    
- existing standards investigation is incomplete.
    

Edge:

**Scope and Start —returns-to→ Understand the Ecosystem**

---

## 5. Return to Aims and Objectives

Use when:

- development outputs are clearer than desired change;
    
- causal logic is weak;
    
- objectives conflict;
    
- the proposed intervention does not plausibly affect the intended outcome.
    

---

## 6. Return to Development Planning

Use when:

- the standard appears justified;
    
- but the chosen method, resources, governance, or testing plan are inadequate.
    

---

## 7. Reuse or Extend

Redirect toward an existing standard.

This is a successful Scope outcome.

---

## 8. Use Another Intervention

The opportunity is valid, but standardization is not the best response.

---

## 9. Pause

The case may be sound, but:

- funding;
    
- participation;
    
- stewardship;
    
- timing;
    
- or infrastructure
    

is not yet sufficient.

Preserve the bundle so the effort can restart without repeating discovery unnecessarily.

---

## 10. Stop

Evidence no longer supports proceeding.

Stopping should generate a brief record explaining what was learned and why development was not pursued.

# Pattern: Development Case, Not Business Case

The final product of Scope and Start is best understood as a **development case**.

A business case asks:

> Is this worth investing in?

A development case asks something broader:

> Is this intervention justified, appropriately bounded, participatory, technically plausible, sustainable, and ready to learn through implementation?

That seems much closer to what an open governance standard needs.

---

# Pattern: The Bundle Is the First Audit Boundary

Scope and Start creates the first durable baseline against which later development can be evaluated.

Later phases should be able to ask:

- Did the scope change?
    
- Did the intended users change?
    
- Did the theory of change change?
    
- Did the core features expand?
    
- Did sustainability assumptions prove false?
    
- Did new power relationships emerge?
    
- Were approval conditions satisfied?
    
- Are we still building the standard that was justified at the end of Scope?
    

Changes are not failures.

Unrecorded changes are.

---

# Pattern: Crossing the Gate Creates Obligations

Once Development begins, the effort inherits obligations created during Scope.

These include commitments to:

- participation;
    
- testing;
    
- openness;
    
- interoperability;
    
- accessibility;
    
- stewardship;
    
- licensing;
    
- documentation;
    
- review.
    

The Scope and Start Bundle therefore functions as both:

**permission to proceed**

and

**a record of the promises under which development was justified.**
